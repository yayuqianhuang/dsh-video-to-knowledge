# Release v0.1.15 · 推 tag 即发版

## 这一版解决什么

以前发一次版要三样东西：本地有 token、有人手动点、正文还要复制粘贴。这一版把它变成一行命令——**推 tag 就发版**，仓库里不存任何长期密钥。

```bash
git tag -a v0.1.16 -m "…" && git push origin v0.1.16
# → Actions 自动建 Release，正文取自 docs/releases/v0.1.16.md
```

## 怎么做的

新增 `.github/workflows/release.yml`，触发条件是 `push: tags: v*`：

| 步骤 | 行为 |
|---|---|
| 解析 | 从 tag 名取 `docs/releases/<tag>.md`；没有则走 `--generate-notes` |
| 幂等 | 先 `gh release view`，已存在就 `gh release edit` 只更新正文，不报错 |
| 鉴权 | 用仓库内置 `GITHUB_TOKEN`（`permissions: contents: write`），运行时临时签发 |
| 汇总 | 在 Actions 的 Step Summary 里写明本次正文来源 |

并发用 `concurrency: release-<ref>` 兜住，避免 tag 连推时互相覆盖。

## 为什么不用 PAT

- **长期密钥进磁盘 = 长期风险**：一旦泄露，攻击面是整个账号（classic）或该仓库的写权限（fine-grained）。
- **内置 token 是临时凭证**：每次运行由 GitHub 签发、跑完即失效，仓库与 Actions 配置里都不留 secret。
- 副作用是撤销也很自然：哪天不想要自动发版，删掉这个 workflow 即可，没有"记得去吊销"的负担。

## 边界

- 正文文件缺失时**不会失败**，退化为 GitHub 自动生成的 release notes（按 commit 归类的 "What's Changed"）。
- 已存在的 release 只改正文，不改 draft/prerelease 状态、不删附件。
- 私有仓库同样适用（`contents: write` 对同仓库有效）。

## 升级

不需要升级插件本体——这是仓库侧的 CI 配置。拉一下 `main` 即可看到。
